## 저장 계약

- 파일 선택·교체·삭제·대표 순서와 일반 정보는 메모리 초안이다. 저장 전에는 업로드 예약도 만들지 않는다. 취소하면 기존 공개 사진/필드는 유지한다.
- 사진 변경이 있을 때 `api.save_animal_edit(p_animal_id,p_data,p_assets,p_expected,p_request_id)`로 7개 일반 필드와 사진 asset ID 전체 배열(0~3장)을 한 트랜잭션으로 저장한다. 첫 사진이 대표다. 사진 변경이 없는 일반 편집은 기존 `update_animal`을 유지한다.
- 일반 필드의 엄격한 자료형·필드 집합·Unicode 공백·날짜/enum 검사, 활성/동의/소유권·revision·24시간 영수증을 적용한다. 다른 계정/개체의 asset, 미검증·만료·삭제 중 asset, 중복/4장/잘못된 배열을 거절한다. 공개 여부·성장·개체 순서는 변경하지 않는다.
- 순서는 예산 → 사용량 → 프로필 → asset 잠금이다. 사진 업로드/파일 제거 같은 외부 IO는 DB 트랜잭션 밖에서 수행한다. 저장은 revision 한 번만 증가시키며 실패는 사진/일반 정보/영수증 모두 롤백한다.
- 새 사진은 새 asset/path로 검증한다. 기존 3장이 연결된 상태에서도 새 편집용 준비 사진은 최대3장, 동시 reserved는 계정당2세트다. 검증 후 실제 바이트를 계산한다. 쓰기 중지 시에는 일반 정보/순서/추가 변경 없이 기존 사진을 제거하는 제한 경로만 허용한다.
- 저장된 사진의 공개 DTO는 기존 asset ID/순서뿐이다. 메모·파일 경로·사용량을 공개하지 않는다. 대표 변경은 기존 Worker HTML/공유 이미지 조회에도 반영된다.

## 응답 유실과 취소

업로드한 파일 ID와 요청 영수증을 메모리에 보관해 같은 저장 요청을 다시 보낸다. 저장 결과가 미확인 상태면 필드/사진 변경을 잠그고 같은 요청 재시도 또는 최신 검토를 제공한다. 취소·버리고 이동·최신 검토 전에는 미확인 명령을 같은 키로 다시 처리해 진행 중 저장을 확정/롤백시킨 뒤 실제 dashboard를 조회한다. 조회 실패는 초안·파일 ID·잠금을 유지한다. 최신 검토에서는 일반 필드와 실제 저장 사진을 확인하고 입력 유지/최신값 선택 후 다시 저장한다. 자동 덮어쓰기는 하지 않는다. 최신값 선택 때는 미연결 준비 사진을 정리 대기로 바꾸는 요청이 완료된 후에 재업로드를 허용해 3장 준비 슬롯의 경합을 막는다.

취소는 실제 저장된 사진을 되돌려 쓰지 않는다. 최신 조회에서 연결된 사진을 확인하고 이 편집이 만든 미연결 asset만 정리 요청한다. 전체 문서 이탈은 beforeunload로 경고하며, 끊긴 업로드는 DB 만료/정리 목록에 남는다. 임시 입력이나 파일을 별도의 영구 브라우저 저장소에 보관하지 않는다.

## 파일 정리와 용량

[공식 문서의 서명 업로드 URL](https://supabase.com/docs/reference/javascript/storage-from-createsigneduploadurl)은 2시간 유효하다. 새 Worker는 토큰을 발급한 뒤 서비스 전용 `register_upload_lease`로 DB의 `cleanup_after`를 최소2시간5분 뒤까지 연장한 후에만 토큰을 반환한다. 기존 등록 예약 API의 307,200바이트 계약은 유지하며, 실제 토큰 반환 전에는 버킷 상한225,280×2 = 450,560바이트를 예약해 미검증 두 경로의 최대 사용량을 보존한다. 기존 클라이언트와의 호환 때문에 새 열은 nullable이며, 새 사진 편집 예약은 처음부터 보호 기한/예약량을 가진다. 표시는 기존 220KiB+80KiB 제한으로 인코딩한다.

제거된 사진은 즉시 연결에서 빠져 새 미디어 조회가 거절되며 `delete_pending`이 된다. 보호 기한이 있으면 `cleanup_manifest`는 경로를 내주지 않고 대기를 반환하며 Worker는 `cleanup_pending`을 알린다. 기한이 없는 기존 사진을 새 명령으로 제거할 때도 보수적으로 보호 기한을 설정한다. `finish_cleanup`는 기한 이전 또는 실제 Storage 파일이 남은 상태에서 용량을 반환하지 않는다. 일부만 삭제된 경우도 포함한다. 기존 읽기 서명 URL/이미지는 최대5분 동안 남을 수 있다는 기존 계약은 유지한다.

`npm run local:cleanup`은 기한이 지난 미연결/삭제 대기 파일을 최대50건씩 실제 Storage API로 제거하고 완료 확인 뒤 예약/저장량을 반환한다. 실패 시 상태/사용량은 남고 재시도한다. 앱에서 정리 대기는 여전히 예산에 포함되므로 한도에 걸리면 즉시 추가 업로드를 허용하지 않는다. 운영 자동 정리 스케줄은 외부 콘솔/운영 설정 단계이며 여기서 구성한 것으로 표시하지 않는다.

## 마이그레이션·검증

로컬 SQL로 반복 검증하고 보안 advisors의 경고 이상 항목 없음을 확인한 뒤 CLI `migration new` 작업 파일을 생성했다. 비어 있는 작업 파일을 `db pull --local --schema api,private`의 실제 스키마 출력으로 대체해 `20261028193831_animal_photo_edit.sql`을 생성하고 로컬 이력과 일치함을 확인했다. 기존 DB/볼륨을 초기화하거나 이전 migration/schema snapshot을 다시 적용하지 않았다. CLI의 shadow DB 재현과 `remoteHistoryUpdated` 출력은 `--local` 대상이며 원격 프로젝트 작업이 아니다. 최초 변경 전후 기존 개체 행 해시가 동일했다.

- DB: 기존20+일반 편집55+목록46+사진45. 새 사진 검사는 실제 RPC/권한/트랜잭션이며 일부 asset 검증 metadata는 신뢰된 QA 관리자 fixture로 만들고 실제 파일/바이트는 미디어/E2E에서 검사한다.
- 미디어10: 인증/소유권·create-only·잘못된 바이트·취소의 예약량 유지·기한 이후 실제 정리.
- 새 브라우저8: 저장 전3장/취소/7개 폭, 가득 찬 교체·대표·전체 삭제와 공개/공유·부분 파일 정리, 응답 유실 재시도/취소, 재조회 실패 잠금, 충돌 명시적 검토, 업로드 검증 응답 유실, SPA Back 보호.
