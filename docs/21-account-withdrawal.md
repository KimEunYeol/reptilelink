# 계정 탈퇴와 정리 (#26)

F-01/F-10의 본인 탈퇴를 실제 DB·Auth·Storage·Worker에 연결했다. 사용자가 ‘탈퇴’를 입력해 확인하면 계정을 deleting으로 바꾸고 공개·본인 콘텐츠 접근과 새 쓰기를 먼저 차단한다. 세션 해지를 확인하고, 업로드 임대와 실제 파일 삭제를 거쳐 관련 데이터와 인증 계정을 순서대로 제거한다. 이미 접수된 탈퇴를 active로 되돌리는 기능은 제공하지 않는다.

## 원본과 사용자 흐름

`design/마이페이지-기본정보.png`와 `-m.png` 하단의 회색 회원탈퇴 카드/복구 불가 안내/탈퇴하기를 사용한다. 전체 보드 기본정보 하단(x2650~3650,y2600~4150), 상단 공통 적용/삭제 확인(x1700~4400,y900~1500), PC 안내(x0~4300,y8270~9470)를 확인했다. PC 안내의 본문·팝업은 모바일과 같은 크기/내용이라는 지침을 따른다.

독립적인 계정 탈퇴 입력·진행·실패 화면은 없어 기존 개체 확인창/회색 안내/입력/버튼 패턴으로 최소 확장했다. 새 그림/브랜드/시각 방향은 없다. 활성 회색 버튼/안내에는 제공 팔레트의#666을 사용해 작은 텍스트 대비4.5 이상을 실제 렌더링에서 확인했다. D-01 Google 인증을 유지하며 원본 자체 비밀번호·SMS·광고 수신 입력은 추가하지 않았다. 주변 기본정보 레거시 폼/메인 등 전체 디자인 정합은 #2에 남아 있다.

기본정보에 미적용/미확인 저장이 있으면 탈퇴와 헤더 동작을 막는다. 실제 조회 후 취소·저장 결과 확인을 제공한다. 확인창은 정확한 ‘탈퇴’ 입력, 현재 버전과 요청 UUID를 보낸다. 미확인 요청 중 입력·취소/닫기·앱 내부 Back을 잠그고 같은 요청으로 재확인한다. generic VALIDATION_FAILED를 이미 접수된 탈퇴의 취소 근거로 취급하지 않는다. 버전 충돌이면 최신 상태를 확인한 뒤 다시 입력한다.

정지/승인 대기/프로필 없는 계정도 본인을 탈퇴할 수 있다. 이때 별도 본인 조회는 필요한 revision만 반환하고 콘텐츠를 노출하지 않는다. 진행 화면은 세션 해지/파일 정리/인증 삭제 단계를 구분한다. 실제 정리가 끝나야 완료 문구를 표시한다. 탭 복귀 시 같은 사용자/같은 토큰의 Auth 알림이 기존 편집·미확인 명령을 지우지 않게 했다. 사용자 전환/로그아웃은 기존 데이터를 비운다.

`artifacts/account-26/card-{320,360,390,450,768,1440,1920}.png`와 dialog 동일7폭, 실제390px pending/complete/unresolved 화면을 원본과 비교했다. 키보드/Escape/초점 복귀·가로 넘침·미확인/충돌·기본정보 저장 유실·비활성/무프로필·쓰기 중지·정리 단계 중단/재개를 실제 브라우저로 검사했다.

## 잠금과 접근 차단

`private.write_actor`와 `lock_active_account`가 계정 상태 행을 FOR SHARE로 잠그고 active를 확인한 뒤 기존 project/usage/profile/asset 잠금으로 진행한다. 기존 변이 RPC와 `lock_profile`, 서비스 업로드 완료/임대 등록에 이 순서를 적용했다. 탈퇴는 같은 계정 행을 FOR UPDATE로 먼저 잠근다. 실제 탈퇴 트랜잭션을 열어 둔 상태에서 들어온 저장/예약/완료가 기다린 뒤 ACCOUNT_NOT_ACTIVE로 거절되는 경합을 검사했다. 읽기용 actor/기존 RLS의 active 조건은 유지한다.

접수는 본인 auth.uid·확인 문자열·현재 버전·소유자 범위 UUID/영수증을 검사한다. 프로필 공개/이미지 연결과 개체 사진 연결부터 끊고 모든 본인 파일/예약을 delete_pending으로 보낸다. 계정·콘텐츠·예약/완료 요청은 새로 통과하지 못한다. my_dashboard는 콘텐츠·사용량·개체 정리 이름을 숨기고 최소 탈퇴 상태만 반환한다. 데이터 API 테이블은 기존 역할 권한/RLS를 유지한다.

## 세션·파일·인증 정리

`private.account_deletions`는 접수 시각·요청 UUID·세션 해지/앱 데이터 정리 완료 시각만 보관하는 비공개 RLS 테이블이다. Auth 삭제 응답 유실을 재확인하기 위해 Auth FK를 두지 않으며 최종 확인 후 작업 행도 삭제한다. 토큰·이메일·파일 경로를 작업 행에 저장하지 않는다.

서버는 공식 Auth Admin signOut(global) 성공 뒤 세션 해지 확인을 기록한다. 실패하면 sessions 단계에서 멈춘다. 필요한 경우 소유자가 다시 로그인해 재시도한다. JWT의 암호학적 유효기간과 세션 해지는 다르므로 콘텐츠 차단은 현재 DB 상태에서도 강제한다. 정리 재시도는 Data API가 검증한 JWT의 auth.uid와 이미 존재하는 본인 탈퇴 작업에서 ID를 도출한다. 취소된 세션의 만료 전 JWT가 Auth getUser에서 거절돼도 접수된 본인 작업만 이어갈 수 있고, 새 탈퇴나 콘텐츠 접근은 허용하지 않는다. 만료 뒤에는 재로그인 또는 세션 해지가 확인된 작업의 운영 재시도를 사용한다.

Worker 한 번에는 최대4개 asset만 처리한다. 임대 종료 전에는 삭제하지 않고, Storage remove 뒤 DB가 실제 objects 부재를 확인해야 기존 reserved/stored 용량을 반환한다. 기존 GC/개체 정리 목록은 계정 정리 작업을 제외해 전용 절차가 관리한다. 파일이 남거나 카운터가0이 아니면 앱 데이터를 최종 삭제하지 않는다. 원장에 없는 다른 파일을 임의로 지우지 않는다.

모든 파일 제거 후 개체/메모/성장/링크/SNS/일정/사용량/프로필을 정리하고 Auth Admin deleteUser를 마지막에 호출한다. Auth 오류면 auth 단계가 남는다. 삭제 응답을 잃었으면 getUserById의404와 DB의 auth.users 부재를 확인해 작업을 마친다. 작업 행이 남아 있으면 UI는 진행 상태를 유지한다. Auth 내부 행을 직접 수정·삭제하지 않는다.

초대 허용 목록은 가입 시 invited_user_id로 연결하고 탈퇴 접수 시 원래 초대와 현재 이메일의 허용을 폐기한다. 이메일 변경 뒤에도 원래 초대가 다시 쓰이지 않도록 검사했다. 새 초대 없이 재가입을 허용하지 않는다.

## 운영 재시도

기존 WSL/로컬 Supabase만 사용한다. 새 콘솔/유료 작업/예약 클라우드 작업은 만들지 않았다.

```bash
# 기존 전체 정리 + 최대10개 계정 작업에 각1회/4asset까지 처리
npm run local:cleanup

# 승인된 특정 탈퇴 작업만 처리. 다른 업로드/개체 정리는 실행하지 않는다.
node scripts/local-cleanup.mjs --account <본인-탈퇴-작업의-UUID>
```

서비스 전용 pending_account_deletions/account_deletion_job으로 진행을 확인한다. sessions_revoked=false이면 소유자의 로그인/세션 해지 재시도가 필요하다. files 단계는 임대와 실제 파일 존재/삭제를 확인하고, auth 단계는 Auth API 장애나 미등록 소유 파일 등 실제 거절 원인을 운영자가 확인한다. 관련 없는 파일을 강제로 지워 우회하지 않는다. 계정 상태를 active로 되돌리지 않는다. 재시도는 기존 작업을 이어가며 부분 완료된 바이트를 중복 반환하지 않는다.

## 검증·마이그레이션

추가 DB/Auth44개·Worker/실제 Storage/Auth21개·브라우저12개가 통과했다. 새로 만든 qa-withdraw-* 계정/파일만 삭제하고 기존 브리더·qa-owner·qa-other 및 다른 초대 기록을 보존했다. 장애 주입(세션/Storage remove·거짓 성공/Auth 삭제/삭제 응답 유실)과 임대 시각 조정은 폐기용 QA만의 모의 검증이며 실제 장애나2시간 경과를 주장하지 않는다. 특정 계정 운영 CLI의 실제 완료와 다른 계정 보존도 확인했다.

DB lint/보안 advisors 경고 이상 없음. 스키마는 CLI 빈 작업 파일 생성/제거 뒤 실제 db pull --local의20261029103133_account_withdrawal.sql로 생성했다. 스키마 diff가 데이터 UPDATE를 포함하지 않으므로 기존 초대 연결은 별도 CLI 신규20261029103522_account_invitation_backfill.sql로 분리했다. 참조 Auth 사용자 키를 먼저 잠그고 중복 이메일/이미 연결된 행을 제외한다. 적용 전 유일한 pending 파일임을 확인해 migration up --local로 이 데이터 파일만 한 번 적용했다. 폐기용 미연결 초대를 이전 상태로 재현해 ID 연결·다른 초대 해시 불변·QA 정리를 확인했다. 기존 적용 migration/DB/볼륨은 재생·초기화하지 않았다.

로컬 이력과 shadow 비교를 확인한다. database/schema.sql은 검토 snapshot이다. 필수 전체 구성은 build759개(하네스12·단위43·DB564·미디어31·Playwright109)이며 실제 최종 결과/파일 해시는 로컬 verify 보고서와 PR을 따른다. 외부 Google/Cloudflare/운영 Supabase 콘솔·OAuth/운영 배포는 사용자 데스크톱 단계다. 신규 댓글/반응 등 앞으로 추가할 관계도 탈퇴 정리에 연결해야 한다.
