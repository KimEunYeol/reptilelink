## 실제 재현과 변경

폐기용 실제 계정/Storage/브라우저로 기존 동작을 먼저 재현했다. 자체 사진 예약이 서버에서 성공했지만 응답을 잃은 뒤 재시도하면 자산이1개→2개가 됐다. 프로필은 실제 변형2파일이 저장됐지만 complete가 서버에서 실행되지 않은 실패 뒤 create-only URL 재발급이409로 막혔다. 수정 전 재현2개가 실패한 로그와 이후2개 통과를 구분했다.

자체 사진 등록/편집은 파일 초안마다 같은 요청UUID·개체·파일/인코딩/업로드 변형 상태를 유지한다. api.reserve_self_photo는 기존 reserve_photo_edit의 소유권/동의/self역할/3장·동시예약2세트/20MiB·프로젝트 예산을 재사용하고 영수증에 같은 자산을 기록한다. 같은 개체/UUID는 같은 자산, 다른 개체/작업·취소 우선은 충돌, 만료/삭제대기는 새 예약 없이 거절한다. api.cancel_self_photo_request는 실제 자산을 몰라도 동일 UUID로 취소하고, 취소가 먼저 잠금을 얻으면 tombstone으로 뒤늦은 예약 생성을 막는다. 연결 중 자산은 private.asset_bound로 거절한다. 원본 자기3장/부·모각1장·등록/수정/단일 저장·기존 UUID 없는 API 호환은 유지했다.

사진 편집의 현재 메모리 맵을 WeakMap 키로 사용하며 별도 영구/무제한 UUID 캐시를 만들지 않았다. 최신 사진 확인 뒤에도 같은 맵을 유지해 연결된 준비 파일 상태를 잃지 않는다. 준비 실패 때 예약을 자동 취소하지 않고 같은 UUID로 재확인한다. 제외된 초안/명시 취소·최신 상태 선택에서는 예약UUID와 확인된 연결 자산을 함께 고려한다. 실제 연결 여부를 확인하지 못하면 초안과 잠금을 유지하며, 취소 실패/응답 유실은 같은 취소를 재확인한다. 실제 제거 전 바이트/예약 예산을 반환하지 않는다. 자체 준비 파일은24h 경과 시 새 요청을 조용히 만들지 않고 기존 최신 상태 확인 패턴을 사용한다. 공통 pending/시계 변화·물리 영수증 정리는51 범위다.

Worker의 자체/부모/프로필 경로는 공통 create-only 서명 처리를 사용한다. 저장된 변형의409는 stored 힌트이며 성공/ready가 아니다. 클라이언트가 저장 변형을 덮어쓰지 않고, complete가 두 파일을 실제 다운로드해 WebP/크기/치수/SHA를 검증한다. 실제 손상 파일을 주입한 검사는 ready/필드 저장을 거부했다. upsert나 파일 존재만으로 성공 처리하지 않았다. 기존 제품 오류 영역에 사진 처리/연결 안내를 사용하고 로컬 백엔드처럼 내부 개발 용어를 일반 실패 메시지에서 제거했다.
