# 프로필 좋아요 인계

이슈 #30. 선행 댓글/신고 #28 / PR #29는 리뷰의 보관 배치 지적을 보완한 build861개와 최신 재리뷰를 통과해 main6ff2d2b에 병합됐다. 이번 범위는 F-08 프로필 좋아요·소유자 회원 목록과 내부 알림 저장이다. 알림 화면/읽음 처리·통계는 다음 독립 단계다.

## 상태와 권한

온보딩과 필수 동의를 마친 active 회원이 공개·active 프로필에 좋아요를 누른다. 자기 프로필은 금지하고 `(profile_id,actor_id)` 고유 제약을 둔다. 버튼은 원하는 최종 boolean을 보내며 서버에서 토글하지 않는다. 같은 UUID/본문은 24시간 동안 기존 결과를 반환하고 다른 작업/본문으로 같은 키를 쓰면 REQUEST_CONFLICT다. 새 요청은 변경 없음도 포함해 회원당 고정 시간 창60회로 제한하며 같은 영수증 재전송은 횟수를 소비하지 않는다. 쓰기 중지 중 추가는 막고, 본인 취소는 시간 제한/활성 조건 안에서 허용한다.

좋아요 추가와 알림·영수증·제한 기록은 같은 트랜잭션이다. 이미 눌렀다면 기존 좋아요 ID를 유지하고 알림을 추가하지 않는다. 취소는 좋아요와 연결 알림을 함께 지운다. 취소 후 과거 ‘추가’ 요청을 재전송해도 과거 영수증만 반환하며 좋아요를 되살리지 않는다. UI는 명령의 과거 결과 대신 실제 최신 상태를 읽는다. 공개에는 현재 개수와 활성 호출자의 본인 상태/준비 여부만 반환하며 Auth 이메일/사용자 UUID나 회원 목록을 넣지 않는다.

`private.profile_likes`는 RLS와 일반 역할 권한 회수, Auth/프로필 FK·자기 금지·고유 제약을 가진다. `notifications`는 comment 또는 profile_like 중 정확히 하나의 참조를 강제한다. `(like_id,recipient_id)` 복합 FK와 ID 고유 제약/CASCADE로 수신자 일치·중복 없음·취소 정리를 보장한다. 댓글 알림의 기존 계약도 유지한다.

`my_profile_likes`는 본인에게 도착한 회원 목록만 제한 커서로 조회한다. 공개·active 회원 프로필의 이름/링크/이미지만 조인하고 나머지는 ‘회원’이다. 원본처럼 좁은 창의 아바타·이름 행/더보기를 사용하며 공개 페이지의 소유자 하트에서 연다. 비공개 소유자 목록도 RPC로 허용하며 관리 화면 진입은 후속 통계/알림 흐름에 연계한다.

## 비공개·탈퇴·복구

새 공개 조회는 비공개·중지·없는 대상을 동일하게 숨긴다. `my_existing_profile_like`는 호출자 본인의 기존 행동 여부·취소 준비 여부만 반환한다. 비공개 대상의 이름·이미지·전체 개수는 없다. 비공개 페이지에서 자기 좋아요를 취소해도 페이지를 다시 공개하지 않는다. Worker404는 개인정보 없는 공통 HTML/404/no-store/noindex를 유지하고 앱 자산만 로드한다. 본인 JWT로 조회한 기존 행동이 있을 때만 최소 취소 버튼을 보여준다. 익명/다른 회원에게 페이지 정보가 추가되지 않는다.

탈퇴 요청은 다른 페이지에 남긴 자기 좋아요를 즉시 제거하고 연결 알림을 정리한다. 받은 좋아요는 대상 프로필의 최종 삭제 때 CASCADE로 지운다. 최종 계정 정리에도 자기 좋아요 제거를 연결했다. 상호 탈퇴 시 교차 행 잠금이 생기지 않도록 요청에서 대상의 모든 받은 좋아요를 동시에 지우지는 않는다. 공개는 이미 차단되며 파일 정리를 기다려도 본인의 외부 좋아요가 남지 않는다.

미확인 요청은 정확한 최종 상태/UUID를 유지한다. 응답이나 실제 조회가 불명확하면 하트·개체 열기·Back/Link/문서 이탈을 잠그고 동일 명령으로 확인한다. 24시간 경과는 단조 경과 시간과 보수적인 실제 시각 검사를 사용한다. 보장 시간이 지나면 재전송을 중단하고 현재 상태를 읽은 뒤 사용자가 새로 선택해야 한다. 같은 사용자 토큰 갱신은 요청을 지우지 않으며 실제 사용자 변경에는 이전 요청을 재전송하지 않는다.

공개 개체 댓글과 좋아요가 동시에 router blocker를 등록하지 않도록, 좋아요는 미확인 명령이 있을 때만 이동 보호 자식을 마운트한다. 그동안 개체 팝업을 열지 못하게 한다. 결과 확인 후 댓글의 기존 보호가 정상 작동하는 실제 Back/키보드 회귀를 포함했다.

## 기존 명령과의 요청 키 경합

실제 검사에서 좋아요가 다른 페이지를 잠근 동안 같은 회원의 디자인 저장이 같은 UUID를 사용하면, 기존 명령이 마지막 영수증 INSERT에서 내부 중복 키 오류를 반환했다. 데이터는 롤백됐으나 오류 분류가 잘못됐다. 기존 잠금 순서를 바꾸지 않고 private.record_receipt를 도입했다. 15개 기존 명령의 같은 열 순서 단일 기록만 이 helper로 옮겼다. 충돌 시 REQUEST_CONFLICT를 발생시켜 변경 전체를 롤백한다. 기존 선행 조회·버전·해시·영수증 결과는 유지한다. 새 댓글/좋아요의 claim/replay 방식은 유지한다. 내부 helper는 일반 역할에 열지 않는다.

강제로 첫 트랜잭션을 열어 둔 상태에서 실제 다른 명령을 실행해 디자인 입력/버전이 함께 롤백되는 것을 확인했다. 디자인/댓글과 좋아요의 양방향 키 경합, 좋아요→취소/취소→추가 순서, 이전 시간 창, 동시64개 중60개만 허용, 상호 대상과 파일 대기 중 탈퇴를 검증했다.

## 마이그레이션과 검증

CLI의 빈 작업 파일 생성/제거 뒤 실제 db pull로 `20261029130949_profile_likes.sql`을 생성했다. 추가 활성 계정 조회 조건은 별도20261029132426_like_active_visibility.sql로 생성했고 기존 적용 migration은 바꾸거나 재생하지 않았다. `database/schema.sql`은 검토 원본에 이번 확장을 덧붙인 참고 자료다. 실제 로컬 이력·shadow 차이 없음·보안/성능 advisors 및 타입 lint 경고 이상 없음을 확인한다.
