# 댓글·신고·운영 정리 인계

이슈 #28. 선행 #26 / PR #27은 main f876752에 병합됐다. F-08의 댓글과 신고를 구현한다. 좋아요, 알림 화면과 통계는 다음 독립 단계다. 추가 비용·외부 메일·푸시·실시간 연결은 없다.

## 작성·조회·처리

온보딩과 필수 동의를 마친 active 회원만 공개 개체에 일반 텍스트 1~500자를 작성한다. Unicode 코드포인트로 길이를 검사하고 앞뒤 ECMAScript 공백을 제거한다. HTML은 텍스트이며 답글·멘션·첨부·본문 수정은 없다. 개체당 hidden/deleted를 포함한 보관 중 200개, 회원당 분당3회·한국 날짜별30회, 추가2초 창1회를 서버에서 검사한다. 고정 창 경계의 순간 버스트는 가능하다.

작성자는 자기 댓글을 삭제하고, 소유자는 자기 개체의 댓글을 숨긴다. 삭제 시 본문은 즉시 NULL이다. 다른 회원의 본문 수정·삭제는 불가능하다. 새 댓글과 수신자 내부 알림은 같은 트랜잭션으로 생성하며 자기 행동에는 알림을 만들지 않는다. 알림에는 본문을 복제하지 않는다.

`public_animal_comments`는 현재 visible+개체/프로필 공개+소유자 active를 검사한다. `public_comment`는 숨긴 ID를 직접 조회해도 NULL이다. 작성자 이름·링크·이미지는 작성자의 active 공개 프로필에서만 가져오며 그 외에는 ‘회원’이다. Auth 이메일·제공업체 이름·작성자 UUID·권한·메모는 공개 DTO에 없다. 댓글 테이블의 일반 역할 직접 조회/쓰기를 회수하고 RLS를 켰다. 필요한 최소 RPC만 열었다.

목록은 created_at/id 내림차순 20개와 다음 커서로 조회한다. 서버가 반환한 마이크로초 문자열을 그대로 전달한다. `my_comment`는 작성자/대상 소유자, `my_animal_comments`는 해당 개체 소유자만 읽는다. 비공개 페이지의 숨김 댓글도 개체 수정 → 댓글 관리에서 확인할 수 있다. 공개 카드 수에는 visible 댓글만 포함한다.

요청 UUID·actor별 24시간 영수증에 작업/본문 해시를 검사한다. 같은 요청은 새 댓글·알림·신고·제한 횟수를 만들지 않는다. 다른 작업/본문의 같은 UUID는 거절한다. 상위 공개 조건이 바뀐 뒤에도 이미 커밋한 요청은 같은 명령으로 확인할 수 있다. 프런트엔드는 요청을 보낸 뒤 결과나 실제 조회가 불분명하면 입력·취소·이동을 잠그고 같은 본문/UUID로 재확인한다. 새 조회가 성공한 뒤에만 초안을 해제한다. 저장 전 초안은 닫기/Escape/Back/전체 문서 이탈에서 보호한다.

## 신고와 운영 절차

active 온보딩 회원은 공개 개체 또는 visible 댓글 중 하나를 신고한다. 사유는 spam/abuse/privacy/other, 설명은 최대500자이며 하루5건·추가2초 창1회 제한이다. 서버는 현재 대상/페이지 일치를 검사하고 접수 ID만 반환한다. 다른 사람의 신고 목록은 회원이 읽을 수 없다. 역할을 user_metadata로 위장해도 운영 권한이 생기지 않는다.

운영자는 기존 WSL에서 아래 명령으로 현재 내용을 검토한다. 스크립트는 `localStatus`의 루프백 Supabase만 허용한다. 자격증명을 출력하거나 프런트엔드에 전달하지 않는다. 목록은 오래된 순서20개이고, `next.after`/`next.id`를 다음 조회 인수로 사용한다. 출력에는 신고자 이메일/UUID가 없다. 신고 설명에는 민감한 입력이 있을 수 있으므로 출력·로그를 외부에 게시하지 않는다.

```bash
npm run local:moderate -- list
npm run local:moderate -- list --status resolved
npm run local:moderate -- list --after ISO --cursor UUID
npm run local:moderate -- resolve --id REPORT_UUID --decision hide --request REQUEST_UUID
npm run local:moderate -- resolve --id REPORT_UUID --decision dismiss --request REQUEST_UUID
npm run local:moderate -- prune --actor ACTOR_UUID
```

실제 ID와 새 요청 UUID를 전달한다. 위 자리표시자를 그대로 실행하지 않는다. 검토 후 hide 또는 dismiss를 명시적으로 선택한다. 같은 결정을 다시 요청하면 기존 결과를 반환하고, 반대 결정으로 바꾸는 재요청은 거절한다. 댓글 숨김은 visible을 hidden으로 바꾼다. 개체 숨김은 is_public=false와 소유자 revision 증가를 함께 처리한다. 이는 영구 제재 상태가 아니므로 소유자가 최신 정보를 확인한 뒤 다시 공개할 수 있다. 반복 남용에는 기존 운영 계정 중지 절차를 사용한다. 신고 처리를 제공했다는 것이 실제 운영 신고를 처리하거나 외부 출시했다는 뜻은 아니다.

## 삭제·보관·스케줄

탈퇴 요청은 타인 페이지에 쓴 자기 댓글도 즉시 본문 NULL/삭제 상태로 바꾼다. 파일 업로드 유효기간을 기다리는 동안에도 공개 본문은 남지 않는다. 최종 계정 정리는 자기 댓글·신고·제한 기록과 대상 프로필/개체의 연결 행을 제거한다. 개체의 실제 삭제에는 댓글·신고·알림 FK가 CASCADE로 연결된다. 보관 중인 신고에는 댓글 스냅샷을 별도로 복제하지 않는다.

`private.prune_activity`와 서비스 전용 `api.prune_activity`는 종류별 최대500행을 SKIP LOCKED로 정리한다. actor를 주면 현재 QA/대상 회원으로 제한하고 생략하면 전체 적격 행을 처리한다. 본문은 삭제 즉시 지우며 최소 행은 최대7일, 알림과 처리한 신고는 최대90일, 제한 기록은 최대48시간을 목표로 한다. 매시 실행 간격에 맞춰 삭제 행6일23시간·알림/처리 신고89일23시간부터 정리하고 제한 기록은47시간 후 만료한다. 정상 실행 시 한 시간 안에 남은 여유를 사용한다. 서비스 중단·지속 잠금으로 건너뛴 행·비정상 적체 시 상한을 보장할 수 없으므로 작업 실패와 적체를 운영자가 확인하고 같은 정리를 재실행해야 한다. 서비스 역할로 직접 대량 입력한 자료는 정상 쓰기 한도의 보장이 적용되지 않는다.

기존 로컬 PostgreSQL에 pg_cron1.6.4와 `reptilelink-activity-retention`을 구성했다. 일정은 UTC 매시17분(`17 * * * *`)이며 SQL 정리 함수를 호출하는 익명 SQL 블록을 실행한다. 각500행 배치가 끝나면 커밋하고, 어느 종류든 한도를 채웠으면 다음 배치를 처리해 적격 대상을 모두 소진한다. 단순히 한 시간에 한 배치만 실행하지 않는다. PostgreSQL 운영자로 실행하고, 외부 역할에 새 프로시저/함수를 열지 않았다. [PostgreSQL의 DO/CALL 트랜잭션 제어](https://www.postgresql.org/docs/current/plpgsql-transactions.html)를 확인하고 실제 Cron으로 검증했다. 외부 HTTP·API 키·추가 서비스가 없다. 이 작업 자신의 실행 이력만7일 후 정리한다. 다른 Cron 작업/기록은 변경하지 않는다. [Supabase Cron 설치](https://supabase.com/docs/guides/cron/install)와 [실행·이력 안내](https://supabase.com/docs/guides/cron/quickstart)를 확인했다. 운영 프로젝트의 확장/스케줄 활성화·실제 원격 실행은 데스크톱 배포 단계에서 별도로 확인해야 한다.

## 원본 비교와 차이

`design/링크페이지-m-1.png`의 설명 아래 원형 녹색 아바타→굵은 공개 이름/본문/작은 시각→회색 더보기→둥근 입력창/녹색 작성 순서를 따른다. `링크페이지.png`, `링크페이지-m.png`의 카드 왼쪽 위 댓글 수를 반영한다. 전체 보드 `(7000,6000,1200,1200)`의 댓글 부분과 PC 안내 `(0,8400,5000,1000)`를 확대해 읽었다. PC도 모바일과 같은 콘텐츠 크기/레이아웃이며 상세 팝업은 모바일을 따르라는 설명을 적용했다.

원본 예시의 녹색 @멘션·답글은 채택 F-08/D-05의 초기 제외와 충돌하므로 일반 문자열로만 표시한다. 삭제·숨김·신고·독립 관리의 세부 시안은 없으므로 원본 텍스트 버튼·기존 좁은 창·필드·회색 안내 패턴만 최소 확장했다. 기존 원본 아바타 자산을 재사용하고 새 그림을 만들지 않았다. 익명 쓰기는 허용하지 않는다. 주변 공개 셸/카드 전체·메인/인증의 남은 차이는 #2에서 처리한다. 이 단계가 전체 공개 화면 디자인 완료를 뜻하지 않는다.

로컬 증거는 무시되는 `artifacts/comments-28/`의 public/manage/report-{320,360,390,450,768,1440,1920}.png 및 unresolved-390.png다. 기본 댓글 크기/아바타/줄바꿈과 원본을 직접 대조하고 가로 넘침·하단 조작·키보드를 검사한다. 신고·숨김에 독립 원본이 없다는 한계는 위 재사용 패턴으로 기록한다. Worker는 공개 개체 DTO/댓글 수를 초기 bootstrap에 넣으며 댓글 본문은 JS로 제한 조회한다. 초기 HTML에 댓글 본문·신고 입력을 넣지 않는다.

## 실제 검증과 마이그레이션

신규 DB32개·한도/신고/보관27개·실제 잠금 경합10개·운영 CLI/Cron6개·보관 경계4개·배치 회귀9개, 단위4개, 브라우저10개를 구성했다. 폐기용 새 QA 계정과 현재 실행 ID만 사용하고 원래 브리더/QA fixture를 삭제하지 않는다. 실제 검사는 소유권·직접 API/RLS·500자 Unicode·200개 보관·분당3회/일30회/신고5회·동시 UUID·원자성·공개 상위 차단·역할 위장·서버 커서 정밀도·삭제/탈퇴 경합·응답 유실/실제 조회·Back 잠금·쓰기 중지 축소와 실제 Cron 실행을 포함한다.

첫 브라우저 검사의 관리 버튼 이름을 실제 접근성 이름으로 맞췄고, Back 검사는 동일 주소 링크의 이력 교체를 피하도록 실제 상세→프로필 SPA 이동 이력으로 구성했다. 해당 검사가 통과했다. 신고 하단 버튼이320px에서 넘친 것을 발견해 기존 버튼 패턴에 간격 축소/줄바꿈을 적용했다. 원본과 비교해 아바타40px/본문14px/시각12px로 보완했다. 실제 운영 검증은 새 QA 신고만 숨기고 UUID로 제한한 임시 Cron을 실행한 뒤 그 작업과 기록을 정리했다. 최초852개 전체 검증 후 PR #29 리뷰에서 정상 한도 안의610개 제한 기록을 한 배치로 소진하지 못하는 문제가 지적됐다. 기존 함수의500개 처리/110개 잔존을 재현하고 스케줄을 배치별 커밋/반복으로 보완했다. 실제 Cron의 첫 실행 한 번으로610개 제한 기록·알림·삭제 댓글·처리 신고를 각각 전부 정리하는9개 회귀를 통과했다. 반복 실행이 뒤늦게 잔여 자료를 지워 거짓 통과하지 않도록 실행 횟수1회도 검사한다.

CLI 스키마20261029114522_activity_comments.sql, 새 스케줄 전용20261029114703_activity_retention_schedule.sql과20261029115355_activity_retention_margin.sql, 리뷰 보완용20261029121312_activity_retention_drain.sql을 사용한다. 두 스케줄 파일은 각각 유일한 pending인지 확인하고 해당 새 파일만 한 번 적용했다. 기존 적용 파일의 의미/사용자 자료/볼륨을 유지하며 DB를 초기화하지 않았다. `database/schema.sql`은 기존 검토 원본에 이번 확장을 덧붙인 참고 자료이며 재실행 지시가 아니다. 실제 lint/보안 advisors·이력/shadow·최종 전체 verify 결과와 코드 해시는 로컬 보고서/PR/task를 따른다. 전체 구성은 build861개(하네스12·단위47·DB652·미디어31·브라우저119)다.
