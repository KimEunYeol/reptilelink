## 명령과 데이터

`api.delete_animal(p_animal_id,p_expected,p_request_id)`는 활성 계정·소유권·필수 동의·프로필 revision·24시간 영수증을 검사한다. 예산 → 사용량 → 프로필 → 개체 순서로 잠그고, deleted_at/is_public=false·사진 연결 해제·모든 연결/준비/예약 asset의 delete_pending·소유자 전용 정리 작업·revision 증가·영수증을 한 트랜잭션에서 처리한다. 실패는 모두 롤백한다. 같은 요청의 재전송은 개체가 최종 제거된 뒤에도 영수증을 반환하며 새 삭제/revision을 만들지 않는다. 쓰기 중지 중에도 제한 삭제는 허용한다.

`private.animal_deletions`는 animal_id PK, profile_id, 삭제 시 이름, request_id, requested_at을 보관한다. 복합 소유자 FK와 RLS를 적용하고 일반 역할의 테이블 권한은 없다. dashboard만 본인의 `{id,name,requested_at}` 목록을 준다. 공개 DTO는 변경하지 않는다. animals RLS·dashboard·media_access는 삭제 대기를 제외한다. 삭제 대기 행의 UPDATE와 새 사진/asset 연결은 트리거로 거절해 기존 편집 API로 되살릴 수 없다.

`active_sort_order`는 `deleted_at IS NULL`일 때만 sort_order를 반환하는 명시적 STORED 생성 열이다. 기존 이름의 지연 고유 제약을 `(profile_id,active_sort_order)`로 바꿔 삭제 대기와 남은 개체의 순서0이 충돌하지 않게 한다. 목록 명령은 미삭제 전체 집합만 검증·정렬한다. 등록 개수 계산은 실제 행을 계속 포함하므로 파일 정리 전 삭제로 한도를 우회할 수 없다. 내부 두 열은 dashboard의 개체 DTO에서 제거한다.

## 파일 정리와 복구

Worker POST `/api/animals/:id/delete`는 사용자 토큰으로 삭제를 확정하고, `/cleanup`은 선택한 본인 정리 작업만 재시도한다. actor는 요청 본문에서 받지 않는다. 서비스 전용 `animal_deletion_assets`·`finish_animal_deletion`은 해당 소유자의 작업 또는 삭제 영수증을 요구한다. Storage API `remove`와 기존 `cleanup_manifest`/`finish_cleanup`을 사용하며 storage.objects를 SQL로 삭제하지 않는다.

현재 업로드 토큰의 보호 기한(최소2시간5분)을 유지한다. 기존 기한이 없는 사진에는 보수적인 새 기한을 둔다. 연결 해제 후 새 사진 접근은 즉시 거절하지만 이미 발급된 읽기 URL은 최대5분 남을 수 있다. 기한 전/파일 일부 잔존/정리 실패에는 예약·저장 바이트와 개체를 보존한다. 개별 asset의 실제 파일 제거가 확인되면 그 바이트를 반환하고, 모든 asset이 제거된 뒤 개체·비공개 메모·정리 작업을 최종 삭제한다. 일부 정리만 성공하면 남은 파일/개체가 재시도 대상으로 유지된다.

사진 없는 개체는 첫 요청에서 최종 제거할 수 있다. 사진이 있는 삭제는 본인 dashboard에 정리 대기를 표시하고 ‘정리 다시 확인’으로 재시도한다. `local:cleanup`도 만료 파일 배치 후 최종 개체 작업을 완료한다. 운영 자동 스케줄/외부 콘솔/배포는 아직 구성하지 않았다.

UI는 미저장 편집에서 삭제 진입을 막고, 진입 때 실제 최신 개체를 재조회한다. 확인 전 취소는 쓰기 요청을 하지 않는다. 확인 뒤 응답 유실/재조회 실패에는 같은 요청 ID와 이동 잠금을 유지한다. 닫기/이동도 명령 재확인 및 실제 조회가 성공해야 완료한다. revision 충돌은 최신 이름·상태를 직접 확인한 뒤 새로 삭제 버튼을 눌러야 하며 자동 재삭제하지 않는다.

## 마이그레이션과 검증

기존 개발 DB에서 로컬 SQL로 반복 검증한 후 `db lint --local` 및 보안 advisors의 경고 이상 항목 없음을 확인했다. CLI `migration new animal_deletion`의 빈 작업 파일을 실제 `db pull animal_deletion --local --schema api,private,public --yes` 출력으로 대체해 `20261029042650_animal_deletion.sql`을 생성했다. 로컬 이력이 일치하고 신규 migration까지 별도 shadow에 재현한 `db diff --local` 결과가 비어 있다. 기존 개체의 원래 필드 해시가 변경 전후 동일했다. 초기 migration/schema snapshot 재적용·DB/볼륨 초기화·원격 프로젝트 작업은 없다.

- 새 DB36개: 0/3장과 준비/예약 사진·타인/익명/비활성/동의/입력/revision·영수증/만료/경합·부분 실패 롤백·조회 차단·되살리기 거절·남은 목록 정렬·실제 제거 전20개 한도·메모 cascade·쓰기 중지 삭제.
- 새 브라우저8개: 미저장 진입 차단/취소/7개 폭/키보드·익명/타인 Worker 차단과 사진 없는 삭제·실제3장 삭제/부분 파일 정리/재시도·응답 유실 멱등성·재조회 실패와 Back 보호·명시적 충돌 재확인·남은 목록 적용·쓰기 중지 삭제.
- DB fixture의 일부 검증 metadata와 실제 Storage/WebP 업로드 검사는 구분한다. 브라우저에서 실제 사진을 올리고 한 파일만 남겨 FILES_REMAIN/용량 보존을 확인한 뒤 나머지를 제거한다. 시간 경계는 이번 실행의 QA asset에만 기한을 과거로 옮겨 모사하며 실제2시간 대기를 주장하지 않는다.
- QA는 현재 실행이 만든 ID만 정리한다. 기존 breeder/사용자 개체·사진을 지우거나 전체 정리 배치를 테스트의 일부로 실행하지 않는다. DB/미디어/브라우저는 순차 실행한다.

전체 구성은 production build+278개(하네스12·단위11·DB202·미디어10·브라우저43)다. 최종 전체 검증 결과·파일 해시는 `.local/harness-verification.json`, task12 및 PR에 기록한다. 기존 번들500kB 경고와 실제 OAuth/Cloudflare/운영 배포 미검증은 남는다.


최초 전체 실행은 기존 목록 QA의 SELECT * 복원이 새 생성 열에 값을 넣어 실패했다. 실패 전 trace의 해당 QA 행 하나만 복원하고, 복원 대상에서 생성 열을 제외하며 삭제 전 QA snapshot도 남기도록 보완했다. 같은 목록9개가 모두 통과했다. 이 실패 실행은 최종 통과 증거에서 제외하고 수정/기록을 포함한 전체 verify를 다시 수행한다.
