# WSL 무료 개발·배포 계획 v0.1

기준일: 2026-10-27. 관련 문서: [기능 명세](01-functional-spec.md), [데이터 구조](02-data-model.md).

## 1. 고정 제약

1. 개발·빌드·테스트는 사용자 로컬 WSL에서 실행한다.
2. 추가 지출은 0원. 유료 가입·플랜 변경·유료 체험·결제수단 등록·도메인 구매·유료 API 키 발급·추가 과금 가능한 리소스 활성화는 하지 않는다.
3. 무료 제공량이 있는 종량 과금 상품을 ‘완전 무료 플랜’과 동일하게 취급하지 않는다.
4. 배포 대상은 무료 조직·무료 프로젝트인지 실제 계정에서 확인한다. 기존 계정이 유료 플랜이면 그 조직에 리소스를 만들지 않는다.
5. 한도 초과를 기능 제한·대기·중지로 처리한다. 오류를 해결하려고 자동 업그레이드하거나 다른 과금 서비스로 우회하지 않는다.
6. 개발용 클라우드 프로젝트를 반복 생성하지 않는다. 일반 개발·테스트는 로컬, 무료 클라우드 프로젝트는 배포 검증·운영에 사용한다.
7. 별도 유료 AI API·클라우드 AI 런타임은 사용하지 않는다. 현재 대화의 개발 지원 이용과 별도 API 요금 결제를 혼동하지 않는다.
8. 이 계획은 설계다. 계정 생성·서비스 활성화·배포·패키지 설치를 수행했다는 의미가 아니다.

## 2. 제안 아키텍처

| 영역 | 구성 | 책임 |
|---|---|---|
| 개발 PC | WSL, Node.js, 패키지 관리자, Git | 실행·빌드·검증 |
| 로컬 백엔드 | Supabase CLI와 WSL에서 실행 가능한 무료 컨테이너 엔진 | PostgreSQL·Auth·Storage 검증 |
| 화면 | React + TypeScript + Vite + Tailwind CSS | 모바일 우선 UI·관리 화면 |
| 정적 배포 | Cloudflare Workers Static Assets의 Free 구성 | HTML/CSS/JS/정적 디자인 자산 |
| 최소 서버 | 같은 프로젝트의 Workers Free | 공개 HTML·공유 메타데이터, 변경 명령 진입점, 파일 검증·서명 |
| 운영 데이터 | Supabase Free 조직의 한 프로젝트 | PostgreSQL, 인증, 비공개 Storage |
| 주소 | 제공되는 무료 workers.dev 주소 | 신규 도메인 비용 없이 공개 |
| 테스트 | 타입 검사·핵심 단위/DB 테스트·Playwright | 기능·권한·화면 검증 |

Cloudflare Pages와 Workers를 동시에 기본 운영하지 않는다. 초기 후보를 Workers Static Assets로 통일해 배포와 동적 경로를 한 프로젝트에서 확인한다. 무료 계정에서 이 구성이 실제 가능한지 최초 배포 실험으로 검증한다.

사용자 요청 경로:

- `/assets/*` 등 빌드 파일: 정적 자산 직접 제공. 불필요하게 Worker를 거치지 않는다.
- 관리 화면: 정적 앱 로드 후 인증된 데이터 접근. 첫 HTML에 사용자 데이터를 넣지 않는다.
- `/u/:slug`, 공개 개체 상세: 작은 서버 템플릿으로 공개 데이터와 OG 제목·설명·이미지 경로를 포함한 초기 HTML 생성. 사용자 텍스트는 반드시 이스케이프한다.
- 공개 HTML은 초기에는 no-store로 제공해 비공개 전환 후 새 요청에 과거 정보가 남지 않게 한다. 관리 화면·인증 응답·미디어 서명 응답도 no-store다.
- `/media/*`: 데이터 구조 8.3의 현재 공개 여부 검사 후 짧은 서명 URL 발급. 파일을 임의 외부 URL로 가져오는 프록시를 만들지 않는다.
- 변경 API: 검증된 사용자 JWT로 RLS가 적용된 RPC 호출. 전역·사용자별 제한은 DB에서 원자적으로 검사한다.
- 파일 검증·서명·집계·정리처럼 특권이 필요한 작업만 작은 고정된 서버 경로로 분리한다.

Worker Free의 짧은 CPU 예산을 전제로 대형 서버 렌더러·이미지 재인코딩을 서버에서 수행하지 않는다. 파일 검사·공개 HTML 경로가 실제 예산 안에 들어가는지 측정한 뒤 기능을 확정한다. 실패 시 유료 전환하지 않고 구현을 줄이거나 그 기능을 보류한 상태를 명확히 기록한다.

## 3. WSL 작업 공간

- 실제 배포판·사용자·도구 버전은 개발 시작 시 읽기 전용으로 확인한다. 배포판 이름을 Ubuntu라고 미리 가정하지 않는다.
- 소스 위치는 WSL 내부 `~/projects/reptilelink`를 기본 제안으로 한다. 현재 Windows/OneDrive 폴더를 자동 이동하거나 삭제하지 않는다.
- 로컬 문서·소스의 기준 저장소를 정한 후 Git으로 이력을 이어간다. Windows와 WSL 양쪽에서 각각 node_modules를 설치해 공유하지 않는다.
- Node와 패키지 관리자는 WSL 버전을 사용하고 버전·lockfile을 고정한다.
- 로컬 DB·Storage는 로컬 주소만 사용하며, 원격 자격증명이 없어도 핵심 검증이 가능하게 한다.
- 컨테이너 엔진은 현재 환경·무료 사용 조건·자원을 확인해 선택한다. Docker Desktop 유료 구독이 필요한 상황을 전제로 설치하지 않는다.
- 키는 로컬 환경 파일과 제공업체 secret 설정으로 분리하고 Git에 넣지 않는다. 환경 예시 파일에는 변수 이름만 기록한다.
- 개발 웹·DB 관리 포트를 공인 인터넷으로 공개하지 않는다. 클라우드 무료 배포는 로컬 PC를 상시 서버로 노출하는 방식과 구분한다.

Microsoft는 Linux 명령으로 작업할 경우 WSL 파일시스템에 소스를 두는 구성을 권장한다. [공식 안내](https://learn.microsoft.com/en-us/windows/wsl/filesystems)

## 4. 공급업체 한도와 내부 예산

### 4.1 기준일의 공식 한도

| 서비스 | 공식 무료 범위 중 주요 값 | 운영 의미 |
|---|---|---|
| Workers Static Assets | 정적 자산 요청 무료·무제한 | 앱 파일에 동적 처리를 불필요하게 적용하지 않는다 |
| Workers Free | 요청 100,000회/일, CPU 10ms/요청 | 공개 HTML·API·서명·정리 요청은 한도에 포함 |
| Supabase Free | DB 500MB, Storage 1GB, 일반 egress 5GB/월, cached egress 별도 5GB/월 | 사진 전송과 저장을 각각 관리 |
| Supabase Free | MAU 50,000명, 활성 무료 프로젝트 2개 제한 | 운영 프로젝트 1개로 시작, 소유 계정의 기존 프로젝트도 확인 |
| Supabase Free | 비활성 상태에서 일시 중지 가능 | 복구·중지 안내·로컬 백업 필요 |

Workers 일별 할당량은 UTC 00:00, 한국 시각 09:00 기준으로 갱신된다. 제품의 날짜·통계 기준(한국 자정)과 공급업체 사용량 갱신을 혼동하지 않는다. 월별 할당량의 실제 주기는 제공업체 대시보드에서 확인한다.

근거: [Workers 한도](https://developers.cloudflare.com/workers/platform/limits/), [정적 자산 과금 구분](https://developers.cloudflare.com/workers/static-assets/billing-and-limitations/), [Supabase 요금표](https://supabase.com/pricing), [Supabase Free 청구 안내](https://supabase.com/docs/guides/platform/cost-control).

공식 한도는 변경될 수 있다. 이 표는 서비스 가용성·영구 무료·특정 트래픽 수용을 보장하지 않는다. 실제 배포 전 재확인하고 조건이 맞지 않으면 리소스를 활성화하지 않는다.

### 4.2 앱이 강제할 초기 제한 제안

| 자원 | 초기 제한 | 강제 위치 |
|---|---:|---|
| 브리더 프로필 | 최대 10개, 승인제 | 운영 설정+DB 잠금 아래 검사 |
| 개체 | 계정당 20개 | DB의 쓰기 규칙 |
| 사진 | 개체당 3장 | 예약·연결 시 DB 검사 |
| 저장 공간 | 계정당 20MiB | DB 예약/실사용 카운터 |
| 앱 전체 파일 | 700MiB | 프로젝트 예약/실사용 카운터 |
| 외부 링크 | 계정당 10개 | DB 검사 |
| 일정 | 계정당 20개 | DB 검사 |
| 성장 기록 | 계정당 3,000개 | DB 검사 |
| 댓글 | 개체당 보관 중 200개 | DB 검사 |
| 댓글 쓰기 | 계정당 분 3회·일 30회 | 원자적 action bucket |
| 좋아요 추가·취소 | 계정당 시간 60회 | 원자적 action bucket |
| 신고 | 계정당 일 5회 | 원자적 action bucket |
| 알림·통계 영수증 | 알림 90일·영수증 48시간 | 만료 정리 |

10프로필×20MiB는 최대 200MiB의 계정별 배정이다. 700MiB는 별도 전역 최후 상한이며, 두 값의 작은 쪽과 실제 제공업체 여유를 모두 지킨다. 예약·미연결·삭제 대기 파일도 포함한다.

프로필 한도는 콘텐츠 생성 제한이며 OAuth 호출·모든 외부 요청을 10명으로 제한하는 장치가 아니다. 초기 베타에는 Before User Created Postgres 훅과 비공개 가입 허용 목록을 추가한다. 이 훅은 현재 Free에서 지원한다. 훅 실패·허용 목록 불일치 때 신규 가입을 거절하는지 실제 로컬·원격 OAuth 흐름에서 검증한다. UI의 로그인 버튼 숨김을 보안 장치로 취급하지 않는다. [Auth Hooks 공식 안내](https://supabase.com/docs/guides/auth/auth-hooks)

### 4.3 관찰할 예산과 초과 대응

- 운영자의 정기 사용량 확인에서 DB 350MB, Storage 700MiB, 각 egress 한도의 70%, Workers 일별 한도의 70%를 내부 경고선으로 사용한다. 실측 값·날짜·조치만 기록한다.
- 사용량이 증가하면 사진 크기·조회 개수·보관 기간을 먼저 조정하고 신규 승인·업로드를 잠시 닫는다.
- 애플리케이션 저장 카운터는 공식 전송량·DB 실제 크기·공유 계정의 다른 서비스 사용량과 다를 수 있다. 제공업체 값이 기준이며 DB 카운터만으로 과금·가용성 보호가 완성됐다고 주장하지 않는다.
- 경고선은 운영 기준이다. 모든 공급업체 사용량을 자동 실시간 차단하는 기능을 구현했다고 간주하지 않는다.
- 제공업체가 한도로 요청을 차단하면 503/사용량 제한 화면을 보여주고 반복 요청을 멈춘다. 로컬 데이터로 성공을 가장하지 않는다.
- 무료 플랜을 유지해 추가 청구 경로를 만들지 않는다. 앱 제한은 무료 자원을 오래 쓰기 위한 장치이며 무료 플랜 자체의 과금 정책을 대신하지 않는다.

## 5. 인증·사진·통계의 무료 운영 선택

### 인증

- 첫 배포는 Google OAuth 제안. 시안의 자체 아이디·비밀번호 가입·찾기와 다르므로 사용자 검토 후 명세 상태를 변경한다.
- Supabase 기본 SMTP는 일반 사용자 운영용이 아니다. 별도 무료 메일 발송 경로를 검증하기 전에는 이메일 가입·비밀번호 복구를 배포 완료 기능으로 표시하지 않는다.
- 전화번호 필드는 초기에는 수집하지 않는다. 유료 문자·본인인증을 연결하지 않는다.
- 인증 공급업체의 동의 화면·OAuth 제한·리디렉션·신규 가입 제한을 실제 무료 계정에서 검증한다. 카드 등록이나 유료 기능이 필요하면 중단하고 대안을 기록한다.

근거: [Supabase SMTP 제한](https://supabase.com/docs/guides/auth/auth-smtp).

### 사진

- 상세용 사진 최대 1,280px 긴 변·220KiB, 카드용 최대 480px 긴 변·80KiB를 초기 목표로 한다. 목표 크기로 압축되지 않으면 용량을 늘리지 않고 더 작은 이미지 선택을 안내한다.
- 프로필 최대 320px·100KiB, 배경 최대 1,280px·200KiB. 재인코딩한 JPEG/WebP만 업로드.
- 서버 유료 이미지 변환 API는 연결하지 않는다. 최초 업로드 때 변형을 만들어 보관하고 화면에서 매번 변환하지 않는다.
- 비공개 이미지는 공개 버킷 URL로 전달하지 않는다. 짧은 서명 URL의 추가 요청·캐시 효율 저하도 실측한다.
- 이미지 전송을 Cloudflare로 중계하면 Supabase egress가 사라진다고 가정하지 않는다. 다운로드 횟수가 저장 용량보다 먼저 제약이 될 수 있다.

### 통계·알림

- 통계는 작은 이벤트와 일별 집계로 시작. 모든 방문의 원문 로그를 장기 보관하지 않는다.
- 알림은 페이지 진입 때 조회·수동 새로고침. 상시 실시간 연결·주기적 짧은 폴링은 초기 제외.
- 비필수 통계 수집은 과부하 시 먼저 중단한다. 관리·조회 기능에 비해 우선순위가 낮다.
- 정리는 초기 WSL 관리 명령으로 검증하고, 운영 자동화가 필요하면 무료 Workers Cron 한 개 안에서 묶을 수 있는지 확인한다. 계정의 다른 Cron 사용량도 확인하며 정리 작업은 제한된 배치로 수행한다.

## 6. 구현·검증 순서

### P0. 설계·환경·무료 배포 예비검증

- 사용자 검토 대상 D-01~D-08과 운영 자료를 확인해 문서를 갱신한다.
- WSL 환경과 실제 소스 위치를 확인하고 버전·lockfile·환경 예시·실행 안내를 준비한다.
- 무료 로컬 백엔드와 두 사용자 테스트 데이터를 구성한다.
- 작은 정적 페이지+Worker+테스트 DB 조회를 무료 주소에 배포해 기본 경로를 확인한다.
- OAuth 복귀·가입 제한·사진 예약/검증/서명·공개 메타데이터의 무료 기능 지원과 Worker CPU를 측정한다.
- 사용량·플랜 증거를 기록한다. 유료 기능이나 무료 한도 내 불가능한 핵심 경로가 있으면 설계부터 수정한다.

완료 기준: 한 계정으로 실제 Free 여부 확인, 추가 과금 기능 없음, 로컬 재현 가능, 무료 주소 접근, 핵심 경로 기술 검증 결과 있음. 도구가 성공 메시지를 반환한 것만으로 완료하지 않는다.

### P1. 첫 사용자 흐름

- 로그인·승인·동의 → 프로필 생성 → 사진 포함 개체 등록 → 공개 페이지·상세 보기.
- 계정 격리, 미공개 접근, 동시 용량 예약, 실패 정리, 새로고침 유지 확인.
- 390/450/1440px 시안 비교와 주요 상태·오류 확인.

완료 기준: 두 사용자와 비로그인 상태의 기능·권한 증거, 등록 데이터 유지, 한도 우회 거절, 실제 공유 주소 동작.

### P2. 관리 기능

- 성장 기록·비공개 메모, 링크·SNS, 일정 상태, 디자인 설정.
- 저장 트랜잭션·revision 충돌·정렬·날짜 경계 검증.
- 계정 탈퇴·물리 파일 정리·참조 삭제·토큰 제한 검증.

완료 기준: 단계 B 기능별 수용 기준 충족, 비공개 데이터 노출 없음, 삭제 재시도·복구 가능.

### P3. 반응·운영 기능

- 댓글·좋아요·신고·내부 알림·일별 통계.
- 남용 제한, 재전송 중복 방지, 보관 기간 정리 검증.
- 무료 예산을 유지하는 범위에서 소규모 사용량 확인.

완료 기준: 작성자·소유자·운영자 권한 분리, 신고 대응 가능, 통계 오류가 본문에 영향 없음.

### P4. 출시·복구 검증

- 메인 소개·약관·개인정보·운영 연락처·접근성·반응형 마감.
- 실제 계정 무료 상태, 원격 비밀값 노출 여부, 소스·DB·파일 백업 확인.
- 로컬 복구 실험 후 동일 공개 페이지·사진·권한 확인.
- 배포 버전·검증 결과·알려진 제한·롤백 절차를 기록한다.
- 무료 서비스 중지·전송량 제한·로그인 실패 안내까지 확인한다.

완료 기준: A~C 기능의 증거와 무료 운영 확인, 실제 배포 URL, 로컬 복구 기록. 무료 플랜의 중단 가능성을 없앴다는 표현은 쓰지 않는다.

## 7. AI 개발 작업 단위

한 번의 작업은 예를 들어 ‘개체 등록→저장→공개 카드→소유권 검증’처럼 사용자가 확인할 수 있는 기능 하나다.

작업 입력에는 기능 ID, 관련 테이블, 완료 조건, 이번 작업에서 변경할 범위를 포함한다. 구현 후 타입/빌드, 핵심 DB·권한 테스트, 필요한 브라우저 흐름과 화면 비교를 실행하고 결과를 기록한다. 문서의 요구사항을 바꾸면 같은 변경에서 데이터 구조·검증 항목도 갱신한다.

새 기능에는 무료 자원 영향(요청·저장·전송·외부 서비스)을 적는다. 불필요한 프레임워크·AI 모델 API·유료 테스트 서비스를 추가하지 않는다. 병렬 에이전트 실행은 별도 요청 없이 기본으로 사용하지 않는다.

Figma 화면과 실행 화면 비교는 사용자 허용 범위의 공유 웹 링크/연결 도구와 로컬 앱 브라우저를 사용한다. 데스크톱 Figma 조작을 작업 절차에 넣지 않는다. 이미지 비교 기준은 사람이 시안과 비교해 검토한 실행 화면을 채택하며, 테스트가 통과했다는 이유만으로 디자인 일치를 선언하지 않는다.

## 8. 백업·삭제·복구

- 무료 제공업체의 자동 백업 기능이 포함됐다고 가정하지 않는다.
- DB와 Storage 파일을 별도로 로컬 백업한다. SQL dump만으로 사진이 복구되지 않는다.
- 백업에는 저장 레지스트리·실제 파일·해시·스키마 버전·생성 시각을 포함한다. 비밀 키는 포함하지 않는다.
- 로컬 백업 위치는 사용자 WSL의 비공개 경로를 정해 사용하고 Git·공개 웹·정적 배포 자산에 넣지 않는다.
- 운영 전 백업 보관 기간과 탈퇴 데이터의 백업 내 제거 기한을 정한다. 초기 제안은 최근 7일 보관, 탈퇴 데이터도 보관 기한 후 제거. 복구 직후 탈퇴/중지 상태를 다시 적용하는 검증 절차를 둔다.
- 탈퇴 처리는 공개 중지 → 세션 제한 → Storage 삭제 확인 → 연관 행 삭제 → 인증 계정 삭제다. 일부 실패하면 상태를 남겨 재시도한다.
- 복구 때 개발 테스트 이메일·시안 예시 개인정보를 운영 계정 정보로 덮어쓰지 않는다.

## 9. 현재 완료·미완료 경계

설계 기준 문서는 유지하며 현재 구현·환경 구성·검증 상태는 [진행 기록](05-implementation-status.md)에 기록한다.

원격 인증 공급업체·무료 클라우드 프로젝트·실제 배포·부하·복구 테스트는 아직 수행하지 않았다. 로컬 구현과 원격 운영 완료를 구분한다.

문서 검증은 문서 간 정합성 점검이며 실제 코드·DB 테스트를 대체하지 않는다.
