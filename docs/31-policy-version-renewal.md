# 필수 안내 버전·기존 회원 재동의 (#46)

원본 인증/기본정보/안내 #38 / PR47은 build1099개·head9aae7d4 코드리뷰 completed/no findings·미해결0 뒤 squash 병합했다. 이슈38 종료, 깨끗한 main49f92ea와 검증트리04010554 일치를 확인·보고한 뒤 최신main에서 분기했다.

## 확인한 문제와 구현

새 QA의 기존 프로필에서 동의를 지우자 save_profile은 CONSENT_REQUIRED였지만 /onboarding은 관리로 이동해 재확인할 수 없었다. 16개 함수에 local-preview-v1이 직접 들어 있었고, 일부 기존 생성/업로드 경로는 공통 동의 검사 없이 활성 상태만 검사했다.

private.policy_versions는 이용/개인정보 본문 한 쌍과 버전(1~40 ASCII 문자), 미리보기 여부, 서버 SHA-256 지문을 보관한다. 본문은 각각1~40,000자로 제한한 일반 텍스트이며 HTML로 렌더하지 않는다. 버전 행의 UPDATE/DELETE를 거절해 같은 버전에 다른 본문을 연결하지 않는다. 지문은 버전과 각 본문 SHA-256의 고정 길이 hex를 구분자로 묶어 다시 해시한다. 문서 두 개를 하나의 필수 묶음 버전으로 관리한다.

private.policy_settings의 단일 행은 required_version과 unconfigured/preview/published 모드를 가진다. preview는 미리보기 문서만, published는 미리보기가 아닌 문서만 지정할 수 있다. 새 schema migration에는 본문/설정/동의 INSERT가 없다. 설정 행이 없거나 unconfigured이면 새 동의와 일반 쓰기를 허용하지 않는다. 게시 모드는 기술 설정이며 법적 적정성·자료 확인·출시 승인을 증명하지 않는다.

두 테이블 모두 RLS와 일반 역할/서비스 역할의 직접 권한 철회를 적용했다. 공개 api.policy_context는 현재 본문/버전/지문/모드와 호출자 본인의 최소 확인 여부만 반환한다. 타인 ID/동의 내역/시각은 제공하지 않는다. my_dashboard에는 본인 최소 상태만 추가하며 긴 본문은 넣지 않는다. 비공개 helper는 직접 실행 권한을 주지 않았다.

api.accept_required_policy는 DB 활성 상태·현재 버전/지문·양 필수 boolean을 검증하고 두 동의를 한 트랜잭션으로 기록한다. 기존 (user,kind,version) PK와 ON CONFLICT DO NOTHING으로 같은 확인을 반복해도 최초 accepted_at을 보존한다. 별도의 24시간 요청 영수증을 생성하지 않는 자연키 기반 반복 안전 명령이다. 제시된 버전과 다르면 POLICY_CHANGED, 미준비면 POLICY_NOT_READY, 양 확인 누락이면 CONSENT_REQUIRED다.

기존 필수 버전 검사는 중앙 helper로 통일했다. 일반 write_actor 경로도 현재 필수 동의를 검사하므로 생성/예약/변경의 우회를 막는다. 계정 활성 행→정책 설정 FOR SHARE→기존 예산/프로필 순서로 잠근다. 운영 설정 변경은 같은 설정 행의 UPDATE 잠금을 사용한다. 일반 쓰기의 실패 후에는 원래 요청/입력을 보존하고 재동의할 수 있다. 탈퇴는 별도 기존 경로로 현재 동의/문서 준비 여부와 무관하게 가능하며, 업로드 요청 취소는 동의 요구 없이 기존 활성/소유권/정산 검사를 유지한다. 다른 쓰기의 현재 동의 요구와 서비스 일시중지 중 축소 허용은 별개다.

save_profile의 예전 p_accept_terms=true 호환 경로는 로컬 preview 모드의 local-preview-v1 신규 프로필에만 남긴다. 기존 프로필 재동의나 새 운영 버전에 이 boolean을 사용할 수 없다. 현재 UI는 신규 가입도 표시한 실제 버전/지문으로 명시적 확인 RPC를 먼저 호출한다.

## 원본 화면·복구

회원가입 PC/m와 전체보드 인증/약관을 다시 열어 확인했다. #38의 단일 필수 체크 박스/전체 확인·좁은 흰 스크롤 창·닫기/초점 복구·공통 셸을 재사용한다. 새 장식·법적 예시 본문·마케팅/SMS·자체 비밀번호를 추가하지 않는다. D01/06/07과 기존 가입·미저장/미확인 보호를 유지한다.

안내 페이지/약관 창/동의 입력은 같은 서버 본문을 사용한다. 버전/지문이 바뀌면 체크를 해제하고, 실패 시 성공으로 표시하지 않는다. 기존 회원은 /onboarding에서 재확인할 수 있고 로그인 복귀는 승인·프로필·현재 동의를 갖춘 뒤에만 기존 허용 공개 경로를 한 번 소비한다. 새 가입의 필드/양 필수 확인도 유지한다.

일반 관리 화면은 재동의 요구가 생겨도 열려 있는 편집창을 강제로 교체하지 않는다. 진입 안내와 관련 오류의 ‘새 탭에서 필수 안내 확인’ 링크는 실제 /onboarding을 열며 원래 탭의 초안/미확인 요청을 보존한다. 확인 후 원래 탭에서 다시 시도한다. 알림 폴링이나 토큰/본문의 별도 저장은 추가하지 않았다. 응답 유실은 같은 버전/지문의 확인을 반복해 해결한다. 과거 버전 확인 응답으로 새 필수 버전을 자동 승인하지 않는다.

## 로컬 준비와 데스크톱 입력

npm run local:start는 CLI가 시작한 loopback DB에 scripts/local-policy-preview.mjs를 실행한다. npm run local:policy-preview로도 실행할 수 있다. 이 명령은 기존 local-preview-v1 개발 안내만 불변 버전으로 등록하고 설정이 아예 없을 때 preview를 생성한다. 기존 설정/동의/본문을 덮어쓰지 않으며, 같은 버전에 다른 본문이면 중단한다. 실제 운영 정책이 아니고 원격 실행/게시 명령도 아니다. 기존5계정·자료·볼륨을 초기화하지 않는다. 새 clone/명시적 개발 DB reset 뒤에도 같은 로컬 준비를 사용한다.

실제 운영 주체·법적 본문/수집·보관/연락처·권리는 사용자 데스크톱 입력이다. 확인된 이용약관/개인정보 본문을 새 version, is_preview=false인 private.policy_versions 행으로 넣은 뒤 required_version/모드를 같은 운영 변경 트랜잭션에서 지정하는 것이 입력 지점이다. 파라미터 바인딩이나 SQL 편집기의 안전한 문자열 입력을 사용하고 원본 시안 예시를 복사하지 않는다. 같은 버전 본문을 수정하지 말고 새 버전을 만든다. 설정 변경 트랜잭션에는 회원 행을 함께 잠그지 않아 기존 계정→정책 잠금 순서를 역전하지 않는다.

게시 전 실제 문서 검토, 본문/버전/지문 대조, 새·기존 회원 재확인/취소·실제 Google OAuth·접근/복구를 운영 환경에서 검증해야 한다. 여기서는 운영 문서를 작성/게시하거나 Google·Cloudflare 콘솔/원격 배포를 진행하지 않았다. UI 비활성이나 published 값만으로 서버 보안/법적 완성/출시 가능을 주장하지 않는다.
