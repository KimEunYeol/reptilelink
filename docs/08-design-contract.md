# 디자인·설명 일치 계약

기준일 2026-10-28. 기준은 사용자가 제공한 `design/` 원본이다. 현재 앱이 이 계약을 이미 만족한다는 의미는 아니다.

## 작업 전

1. `design/README.md`에서 해당 PC·모바일 화면과 변형을 찾고 실제 이미지를 연다.
2. `design/렙타일링크_디자인.png`에서 해당 화면 주변의 설명을 확대해 읽는다. 작업 기록의 `design.notes`에 위치(보드 영역/좌표 또는 화면명), 읽은 설명, 구현에 미치는 영향을 적는다. 읽지 않은 부분을 추측해서 전사하지 않는다.
3. 기능 명세 F-xx, 데이터 계약, 디자인 텍스트를 비교한다. 예전 시안의 아이디·비밀번호와 채택된 D-01 Google OAuth처럼 이미 결정된 변경은 근거를 적고 주변의 시각 패턴을 유지한다. 새 충돌은 이슈에 기록하고 의존하는 UI만 보류한다.
4. 등록/편집 팝업, 적용 전후, 빈 상태, 실패, 모바일·PC 범위를 수용 기준에 포함한다. 없는 오류 상태는 기존 폼·알림·버튼 패턴을 조합한다. 새 화면 구조·시각 언어가 필요하면 별도 디자인 결정이 먼저다.

## 구현 기준

- 모바일 우선이며 웹과 앱의 디자인을 동일하게 한다. 전체 보드의 PC 안내는 메인을 제외한 콘텐츠 크기를 모바일과 동일하게 사용하고 상단·하단 영역만 PC에 맞추며, 상세 팝업은 모바일 시안을 따르도록 설명한다. 화면별 실제 원본으로 재확인한다.
- 원본의 콘텐츠 순서, 탭, 카드, 팝업, 폼, 적용 버튼, 색상·간격·곡률·타이포그래피의 관계를 유지한다. 시안에 없는 대시보드, 장식, AI 생성 그림, 임의 로고나 별도 브랜드 스타일을 만들지 않는다.
- 원본에 있는 패턴을 재사용한 보완만 가능하다. 정확한 폰트/자산이 없거나 권한이 확인되지 않으면 근거와 남은 차이를 기록한다. 라이선스를 추정해 외부 배포하지 않는다.
- 목록의 ‘적용하기’와 항목 팝업의 ‘저장’을 구분한다. 텍스트만 같고 실제 저장 동작이 다른 경우 완료 처리하지 않는다.
- 원본 PNG는 비교 기준이지 런타임 화면 전체를 이미지로 대체하는 수단이 아니다. 접근 가능한 HTML과 실제 데이터로 구현한다.

## 검증과 증거

`harness/tasks/<issue>.json`의 `design`에 `applicable`, 원본 `references`, 보드 설명 `notes`, 패턴 재사용/명세 차이 `review`, 검증 증거 `evidence`를 기록한다. UI 수정은 코드와 로컬 Worker 템플릿을 모두 포함한다. UI 수정 시 `applicable=false`로 통과할 수 없다.

기능 명세의 360·390·450·768·1440·1920px 및 최소 320px 조작을 확인한다. 작업별 필요한 캡처·기능·키보드·가로 넘침 검사를 수행하고 실제 확인한 폭과 미확인 폭을 적는다. 캡처는 무시되는 `artifacts/`에 보관하고 PR에는 비밀정보가 없는 증거만 첨부한다. 관련 폭을 검증하지 못했다면 `review.status=blocked`와 사유를 기록한다.

하네스는 파일 존재·체크섬·기록 필수 항목을 검사한다. 이미지의 의미, 디자인 유사도, 설명과 실제 동작의 일치는 자동 판정하지 않는다. 에이전트의 원본 비교와 사용자의 PR 검토가 필요하다.

## 기존 차이

현재 `src/components/Gecko.tsx`는 원본에서 추출한 자산이 아닌 수제 SVG다. 메인·관리·공개 화면의 원본 일치도도 전체 폭에서 검증되지 않았다. 이를 승인된 기준으로 재사용하지 않는다. 원본 준수 정비는 별도 이슈에서 화면 단위로 진행하며 이번 하네스 작업이 UI 수정까지 완료한 것으로 보고하지 않는다.
